# Leaderboard and puzzle suggestions

Playing, joining the leaderboard and suggesting a puzzle require no sign-in. Players opt in with a display name. The website stores suggestions and leaderboard events in **two separate Google Forms with private response records**. The leaderboard form's responder access is restricted to its owner; players submit through the website's receiver. The public leaderboard exposes only the selected player summary described below.

## Player leaderboard

A player chooses a public display name once and keeps the same browser identity across rounds and retries. Repeated names are allowed and do not merge records. The browser generates a random UUID player identifier and a separate random UUID bearer key. The key is saved only on that device and sent in POST bodies over HTTPS; it must never appear in links, screenshots, public data, logs or analytics. The server stores only its SHA-256 hash. A display name alone cannot recover or modify another player's identity. Clearing site data or switching devices creates a new identity; this is not account-based cross-device sign-in.

The public summary includes the display name, unique attempts, unique rounds played, unique rounds completed, the number of rounds with eligible timed results, and each round's best eligible time with assistance counts. It also publishes `latestAt`, the latest included attempt's recorded finish time (or start time while active), and each winning time's `completedAt`. These are actual recorded browser dates, represented as ISO UTC timestamps; the interface may display them in the viewer's local time zone. An active or restarted attempt counts as an attempt and as a round played. Completing the same round repeatedly does not inflate the completed-round count. Practice and gene completion count toward participation, but do not enter the timed image ranking. The player can inspect their individual attempt history on their own device. The public API never returns the complete attempt history, private server event timestamps, bearer keys, key hashes, signatures, suggestion data or contact information. An empty profile has `latestAt: null` and no best-time entries; no result or date is invented.

Times are **self-reported browser times**, not verified competition results or measures of genetic knowledge. There is no server-side game clock or anti-cheat service. Format validation and authenticated updates prevent accidental duplicates and one browser identity overwriting another; they do not establish that a person played fairly. Assistance is permitted and disclosed. A time is eligible only for a complete 12-piece image puzzle in Timed mode, without gene autofill, with a consistent start and finish and elapsed time of 1 second through 7 days. The clock starts at the first correct placement and includes time away from the page.

The overall leaderboard also displays a clearly labelled sample entry: Sasha Gladkikh, 10 rounds, 9:23. This illustrative total lives only in the presentation layer, below any ranked results. It has no rank, individual round times, or completion dates and is never submitted to the private event log or included in the public player API. Real attempts from the same person remain separate. Remove `LEADERBOARD_SAMPLE` and its rendering when an example is no longer needed.

Each attempt has a UUID and increasing revision. A restart starts a new attempt; progress updates retain the original attempt ID. The receiver reconstructs the latest snapshot from the durable event log, so retries do not create extra attempts even after cache eviction. Identical revisions are acknowledged, conflicting equal revisions reject, and delayed older revisions are acknowledged without replacing newer progress. Attempt status may advance from active to completed or restarted; finished outcomes cannot be rewritten. A batch of at most 20 attempts is validated entirely before any event is appended. A successful response acknowledges exactly the requested attempt IDs and revisions.

Choosing to leave removes the player from the public board after server confirmation. The private owner event record and on-device history remain, including the opt-out event. This retains the conference record without keeping an opted-out name visible. Rejoining from the same device uses the same identity and history. Explain this distinction in the interface; do not describe leaving as deletion of all stored data.

Joining, renaming and leaving also use a separate, monotonically increasing action revision. Retries retain the same revision; a new explicit intent advances it. Older requests are acknowledged without changing membership, and equal revisions with different names or actions reject. Even a leave for an unregistered identity creates a private authenticated opt-out record. This prevents a timed-out join that executes later from making the player public again. Clients apply a membership receipt only if its revision still matches the latest local intent. A later deliberate rejoin uses a higher revision.

### Private event storage and maintenance

`server/google-forms/Leaderboard.gs` runs beside the suggestion receiver in the existing Apps Script project, using the already authorized Forms scope. Run `setupLeaderboard()` manually as the owner. It initially creates an unpublished form with one required paragraph question, **Leaderboard event**, disables email collection, response summaries, response editing and one-response restrictions, and stores its ID in `GREGOR_LEADERBOARD_FORM_ID`. It generates the signing key in `GREGOR_LEADERBOARD_SIGNING_KEY`. Setup logs the private editor URL before checking readiness. In that editor, restrict responder access to the owner, then publish the form and enable responses. Do not select general public responder access. Google requires a published, accepting form even for owner-side programmatic writes; unpublished forms cannot receive the event log. Setup never publishes or changes responder access automatically. Run setup again after configuring restricted publication. It reuses the existing form and signing key, verifies writes with one test response, and immediately deletes only that test response. Its execution log and return value include the private editor URL for the owner; the public web handlers never return this URL.

Keep the form and its editor URL private. Download or inspect the owner's response record through Google Forms when an event record is needed. The record contains signed JSON events for registration, name changes, attempts and opt-outs; it is not the public leaderboard table. Never copy that export or the signing key into GitHub, a public spreadsheet or the built site. The setup refuses to use the suggestion form's ID. Leaderboard code must never open the suggestion form or read any of its responses.

Every stored event is HMAC-SHA256 signed using the server-only key. Unsigned, malformed or forged native-form responses are ignored. Signed records with inconsistent structure or history fail closed. Do not rotate the signing key, edit existing events, or remove response rows casually: the durable log is the source of player identity and attempt state. Back it up privately before a deliberate migration. The receiver stops with an explicit maintenance error at 20,000 source responses rather than silently truncating the board. At that point, archive a season or migrate storage with explicit continuity rules.

Public summary responses may be cached for up to 30 seconds; writes invalidate this cache both before persistence and after confirmed persistence. Cache-miss reads acquire the same script-wide lock as writes, recheck the cache after acquiring it, and keep the lock through reading and caching the summary. An overlapping read therefore cannot cache a stale summary while a new result is being stored. Writes use generous circuit breakers of 240 new events per minute globally and 30 per player. These are capacity controls, not proof of identity or a complete spam-prevention service. A valid duplicate receipt remains available when the write limit is reached. Backend errors must retain the player's outbox for retry instead of presenting an empty board or falsely confirming synchronization.

For moderation, set `GREGOR_LEADERBOARD_HIDDEN_PLAYERS` in Apps Script's script properties to a JSON array of public player UUIDs, for example `["82b79a65-04fa-411e-b7dc-71bb190eecb4"]`. These identities are omitted from the public summary without altering the private event history. Cached boards expire within 30 seconds. Remove an ID from the array to restore visibility. Invalid moderation configuration fails closed. Do not put names or email addresses in this property.

To exclude automated test attempts while retaining the player and their future genuine attempts, use `GREGOR_LEADERBOARD_EXCLUDED_ATTEMPTS`, a JSON array of individual attempt UUIDs. Excluded UUIDs do not contribute to public attempt counts, rounds, best times, totals or latest activity dates. Their original signed events remain unchanged in the private owner record. Retries and later revisions of the same UUID remain excluded. A different future attempt UUID is counted normally. If every attempt is excluded, the player remains visible with zero participation, no ranked times and no latest date. Never replace a test time with an invented human time.

The owner-only helper `excludePlayerAttemptsBefore_(playerId, cutoffMs)` can populate this list. Run it from a temporary owner script using the player's UUID and a fixed positive Unix timestamp in milliseconds, no later than the current time. It validates the private event history, acquires the same script lock used by readers and writers, and snapshots the currently known attempt UUIDs for that player whose recorded `startedAt` is at or before the cutoff. It appends these UUIDs to existing exclusions, invalidates the public cache, and returns only `{matched, added, totalExcluded}` counts. It does not create an ongoing date rule, hide the entire player, or change response rows. The helper is not reachable through any public GET or POST action. Invalid exclusion configuration fails closed; an oversized list requires a deliberate storage migration instead of truncation.

After updating either server file, deploy a new version of the existing web app so the endpoint URL stays stable. Test owner setup, account-free joining, an attempt update and retry, renaming, opt-out, and a fresh public GET. Confirm the default health check still does not read any form. GitHub issue-based score submission is legacy code and is no longer the player-facing leaderboard workflow.

## Suggest a puzzle

The home page contains a branded HTML form. A gene or condition (or both) and clinical features are required; reference, name, and email are optional. Contact fields sit in an optional disclosure. Submission requires no Google or GitHub account. `game/suggestions.mjs` validates input, then sends a cross-origin JSON POST with `Content-Type: text/plain;charset=utf-8` to the deployed Google Apps Script endpoint. The receiver validates the request again and saves it as a private Google Form response. The clinical-features answer uses the existing `phenotypes` field and Google Form question.

Success appears only after an HTTP-success response containing `{ok: true, receipt: "…"}`. A blocked request, timeout, malformed response, or server rejection keeps the entered text and offers retry and the native Google Form as a fallback. Retrying an unchanged suggestion uses the same request ID. The receiver caches a payload hash and opaque receipt for up to six hours, providing best-effort duplicate protection; cache eviction or service failure can still permit a duplicate. Editing the suggestion creates a new request ID. Values and contact details stay in memory until submission or page close; they are not saved in browser storage, URL parameters, analytics, or GitHub issues. A confirmed success clears the form.

Client limits are 60 characters for gene, 160 for condition, 2,000 for phenotypes, 500 for reference, 100 for name, and 254 for email. Line breaks are allowed in phenotypes; other control characters are rejected. References must be complete HTTP or HTTPS URLs without embedded credentials. Optional email addresses are validated, and a hidden website field is used as a spam trap. The public endpoint URL is not a credential; owner access and response-writing logic remain server-side.

Responses are private to the form owner and explicitly authorized team collaborators. Optional contact details are for following up on a suggestion. Do not publish responses, contact details, or a response spreadsheet in this repository, the leaderboard snapshot, or the built site. Keep response summaries unavailable to respondents, automatic email collection off, and any organization-only or one-response sign-in restriction off.

Request published gene–condition information only, with no patient details, personal genetic results, or unpublished family data. A suggestion is a request for future educational content, not validation of the association. Before building a round, review its gene–condition evidence, mechanism, inheritance, phenotypic variability, and references through the existing scientific review process.

When changing the form or receiver, confirm the branded website form works in a signed-out browser, accepts a gene-only or condition-only suggestion without name or email, and shows confirmation only after the response is stored. Test retry, invalid input, an unavailable receiver, and a narrow phone screen. Validation must reveal any collapsed optional fields before focusing an invalid value. The native Google Form remains a no-script and error fallback. It retains its original required gene and condition questions; enter “Not specified” for the unknown field when using that fallback. Keep its responder URL current in the home page and `game/suggestions.mjs`; never publish an editor or response-sheet link.

### Maintain the receiver

The deployed Apps Script source is versioned in `server/google-forms/Code.gs`. It executes as the form owner with only the Google Forms OAuth scope and accepts anonymous requests. Its default GET endpoint exposes protocol readiness only, never submitted suggestions. An explicit `?action=leaderboard` request is handled separately by `Leaderboard.gs` and reads only the separate leaderboard form. The exact six question titles, item types, and required flags are checked before any write. Gene and condition remain required in the native form, while the receiver requires at least one in the submitted payload and records a missing counterpart as “Not specified”. This compatibility mapping preserves the existing form schema. It occurs after validation and request hashing, so retries of the same normalized payload retain their receipt. Changing the form schema requires a coordinated receiver update.

After editing the receiver, update the existing web-app deployment to a new version so its URL stays stable. The client endpoint is `SUGGESTION_ENDPOINT` in `game/suggestions.mjs`. Keep it empty until deployment is authorized and tested; never publish a nonworking connection. Test a clearly labelled submission from the site and verify it in the owner's Google Forms Responses tab before release. The built site includes client files only, with no Google credentials or response exports.

## Player API

All player POSTs use `Content-Type: text/plain;charset=utf-8` and schema `gregor-player-v1`, with `action`, `playerId` and `token`. `profile` also supplies `displayName` and a positive integer action `revision`; `attempts` supplies 1–20 attempt records; `leave` supplies its action `revision`. Successful responses contain `ok`, `schema` and `playerId`. Profile and leave responses echo the requested action `revision`, including an older revision acknowledged without a state change. Attempt responses contain `accepted: [{id, revision}]`. Unsupported fields reject. Credentials belong only in the POST body.

Only GET `?action=leaderboard` returns the public `gregor-player-board-v1` summary. It includes `ok`, `schema`, `updatedAt`, and `players`. Each player contains `id`, `displayName`, `attempts`, `roundsPlayed`, `roundsCompleted`, `timedRounds`, `totalBestSeconds`, `latestAt`, and `best`. `latestAt` is ISO UTC or null when no included attempt exists. Best entries contain only `roundNumber`, `seconds`, `hints`, `peeks`, `geneHintsSeen`, and ISO UTC `completedAt` from that winning attempt. Elapsed times are seconds and can contain fractions; rank from the underlying values, not the formatted labels. A failed load returns an error, never a fabricated empty success.

The attempt schema is exactly `id`, `roundNumber`, `revision`, `status`, `mode`, `route`, `pieces`, `startedAt`, `finishedAt`, `seconds`, `hints`, `peeks`, `geneHintsSeen`, and `eligible`. Round numbers are the explicit `01`–`10` catalogue. Status is active/completed/restarted, mode practice/timed, and route image/gene. Practice has null seconds; active has null finish. A first-action gene completion may have zero placed pieces. Only eligible image completions enter timing comparisons. Rendering code inserts all display names and other external strings as text, never HTML.

Google references: [Forms service](https://developers.google.com/apps-script/reference/forms), [FormResponse](https://developers.google.com/apps-script/reference/forms/form-response), and [HMAC utilities](https://developers.google.com/apps-script/reference/utilities/utilities).
